# ChurnCast

**An MLOps pipeline for subscriber churn prediction.**

> ### ⚠️ Prototype disclaimer
>
> **ChurnCast Prototype using KKBOX-like Synthetic Data.**
>
> This prototype uses deterministic synthetic data designed to mimic the structure
> and behaviour of the KKBOX churn dataset. The prototype demonstrates the ChurnCast
> MLOps architecture and software workflow; its evaluation metrics must not be
> interpreted as official KKBOX benchmark results.
>
> The dataset is generated by `scripts/generate_sample_data.py` with a fixed seed.
> No data is downloaded from the internet. Real KKBOX files can be swapped in
> later without redesigning the pipeline — see [Replacing the synthetic data](#15-replacing-the-synthetic-data-with-official-kkbox-data).

---

## 1. Project overview

ChurnCast predicts whether an active subscriber will fail to renew within 30 days
of their membership expiry, and serves that prediction through an API and a web
interface where an analyst enters only a subscriber ID.

The emphasis is on the **MLOps lifecycle** rather than on the model alone: data
generation, leakage-aware feature engineering, temporal evaluation, experiment
tracking, a model registry with a promotion gate, API serving, drift monitoring,
scheduled retraining and containerised deployment.

**Current results** (synthetic data, seed 42, held-out December cohort):

| Model | Validation ROC-AUC | Validation PR-AUC | Test ROC-AUC | Test PR-AUC |
|---|---|---|---|---|
| Logistic Regression | **0.7835** | 0.6966 | **0.7957** | 0.6904 |
| Gradient Boosting (XGBoost) | 0.7824 | **0.7044** | — | — |

Logistic Regression won on validation ROC-AUC and was scored once on the test
cohort. Full numbers: `reports/model_metrics.json`.

## 2. Architecture

```
          Synthetic data generator  (scripts/generate_sample_data.py)
                        |
                   Data ingestion            src/pipeline.py :: step_ingest
                        |
              Validation / cleaning          src/features/features.py
                        |
        Leakage-aware feature engineering    per-subscriber observation cutoff
                        |
                  Feature table              data/processed/features.csv
                        |
          Temporal train / val / test        split by cohort month
                        |
                 Model training              LogisticRegression + XGBoost
                        |
                Model evaluation             ROC-AUC, PR-AUC, P/R/F1
                        |
             MLflow experiment tracking      params, metrics, artifacts
                        |
              MLflow Model Registry          ChurnCastModel + promotion gate
                        |
               FastAPI model serving         /predict/{msno}
                        |
                 Next.js frontend            enter an ID, get a prediction
                        |
          Airflow retraining  +  Evidently drift monitoring
                        |
                Docker Compose stack
```

### The leakage rule

Each subscriber has their own **observation cutoff** — the membership expiry date
the churn question is asked about. Features may only read records dated on or
before it. The renewal transaction that *defines* the label is written strictly
after the cutoff, so a correct feature builder never sees it.

This is enforced in code (`src/features/features.py`) and tested
(`tests/test_features.py::test_post_cutoff_transactions_are_ignored`), not left
to convention. `membership_expire_date` is excluded from the feature space
entirely, because the label is defined against it.

## 3. Dataset

Generated into `data/raw/`:

| File | Rows | Contents |
|---|---|---|
| `members.csv` | 7,500 | city, age, gender, registration channel and date |
| `transactions.csv` | ~69,600 | plan, price, amount paid, auto-renew, cancel flag, dates |
| `user_logs.csv` | ~519,000 | daily play counts by completion bucket, unique songs, seconds |
| `train.csv` | 7,500 | `msno`, `is_churn` |
| `cohorts.csv` | 7,500 | `msno`, cohort month, observation cutoff |

Churn rate ≈ **0.304**. Subscriber IDs are deterministic: `SYN000001` … `SYN007500`.

Cohorts span six months, which is what makes the temporal split possible:

| Cohort | Split |
|---|---|
| 2024-07 … 2024-10 | train (5,030) |
| 2024-11 | validation (1,235) |
| 2024-12 | test (1,235) |

```bash
python scripts/run_pipeline.py
```

Runs ingest → build_features → train → evaluate → register_if_better, then a
drift report. Takes about 40 seconds. Writes a summary to

## 7. MLflow

Tracking is local SQLite by default (`mlflow.db`). To view runs:

```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5000
```

Each run logs parameters, dataset sizes, seed, feature count, all six metrics,
the serialised model, and the confusion matrix / ROC / PR / classification-report
artifacts. The registered model is **`ChurnCastModel`**.

**Promotion gate** — `register_if_better` compares the candidate's validation
ROC-AUC against the best already-registered version. A candidate that does not
improve is rejected and the incumbent stays. Observed in a real run:

```
registered ChurnCastModel v2 (val_roc_auc=0.7835 > incumbent 0.7814)
candidate val_roc_auc=0.7835 did not beat incumbent 0.7835; keeping existing model
```

### curl

```bash
curl -X POST http://127.0.0.1:8000/predict/SYN000001
```

Response:

```json
{"msno":"SYN000001","churn_probability":0.3087,"predicted_label":0,"risk_level":"LOW","model_version":"2"}
```

Risk bands are configurable (`CHURN_RISK_LOW_THRESHOLD`, `CHURN_RISK_HIGH_THRESHOLD`)
and defined once in `src/config.py`: `<0.40` LOW, `0.40–0.69` MEDIUM, `≥0.70` HIGH.

Unknown subscriber → **404** `{"detail":"Subscriber SYN999999 not found"}`.

```bash

```

Enter a subscriber ID, press **Predict Churn**. The page shows churn probability,
prediction, risk level and model version, plus a collapsible read-only subscriber

## 10. Airflow

DAG: `pipelines/dags/churncast_retrain.py`

```
ingest → build_features → train → evaluate → register_if_better
```

Weekly schedule, `retries=2` with exponential backoff. Every task is a thin
wrapper over a function in `src/pipeline.py`, so no business logic is duplicated
in the DAG and the same steps can run without Airflow via `scripts/run_pipeline.py`.

> **Not installed on the host.** No Airflow release supports Python 3.13, which
> is the development interpreter here. The DAG is intended to run in the Airflow
> container in `docker-compose.yml` (Python 3.11). Its structure has been
> validated and the functions it calls are exercised by the pipeline script and
> the test suite, but **the DAG has not been executed in a running Airflow
> scheduler.**

## 15. Replacing the synthetic data with official KKBOX data

The pipeline depends on the **column contract**, not on the generator. To switch:

1. Place the real KKBOX CSVs in a directory with the expected filenames
   (`train.csv`, `members.csv`, `transactions.csv`, `user_logs.csv`).
2. Provide `cohorts.csv` with `msno`, `cohort_month`, `observation_cutoff` — the
   per-subscriber observation cutoff. For KKBOX this is derived from the
   membership expiry the label is defined against; `data/raw_kkbox_original/WSDMChurnLabeller.scala`
   is the authoritative definition (`historyCutoff = 20170131`, candidates
   expiring 2017-02-01 … 2017-02-28).
3. Point `CHURNCAST_RAW_DIR` at that directory and set `TRAIN_COHORTS` /
   `VAL_COHORTS` / `TEST_COHORTS` in `src/config.py` to the real cohorts.
4. Re-run `python scripts/run_pipeline.py`.

For the very large real `user_logs.csv`, `src/data/features_v3.py` contains a
chunked streaming aggregator that keeps peak memory bounded by chunk size rather
than file size.

**The real KKBOX files that were in this repository are preserved in
`data/raw_kkbox_original/`.** They were moved, not deleted, when the synthetic
dataset was generated.

## 16. Limitations

- **Synthetic data.** Metrics reflect a generated process whose churn mechanism
  is known by construction. They are not KKBOX benchmark results and should not
  be compared against published KKBOX leaderboard scores.
- **Airflow not executed.** DAG structure validated; never run in a scheduler.
- **Docker not verified.** Configuration written; never built or started.
- **Calibration not independently reported.** Both models are wrapped in
  `CalibratedClassifierCV` (sigmoid, 3-fold), so probabilities are calibrated by
  construction, but a reliability curve is not currently produced as an artifact.
- **`/predict` fills omitted features** with training medians/modes so the model
  always receives its full column set. This is documented rather than hidden, but
  it means a sparse payload is scored against a partly-average subscriber. The
  primary path, `/predict/{msno}`, uses the subscriber's real feature vector.
- **Single decision threshold.** 0.5 by default, not tuned for any business cost
  ratio.
- **No authentication** on the API — it is a local prototype.
